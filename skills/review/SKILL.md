# Review

Every PR I mention in chat is a link, `[#1234](https://github.com/edstart/platform/pull/1234)`, with its title when I list several: in every report, status line, aside and list, not just the first mention.

1. List the author's open PRs with `gh pr list`, or for "PRs assigned to me" the open PRs requesting my review (`gh pr list --search "review-requested:@me"`). Don't review merged or draft PRs.
2. Check whether I (the signed-in `gh` user, `@me`) have already reviewed each one, and on which commit.
   - Head unchanged since my review: skip it. It's up to the author.
   - Head moved: compare the PR's own patch then and now (`git patch-id --stable` on `git diff <merge-base> <reviewed>` against `git diff origin/<base>...origin/<head>`). If they're identical, only the base was merged in, so skip it. Otherwise review only the new commits (`git log <reviewed>..origin/<head> --not origin/<base>`).
3. Read each PR body before reviewing, and act on any section addressed to the review agent.
4. Run a wcgw agent per PR, scoped to the PR's own diff against its base. It reads branches with `git show origin/<head>:<path>`, and doesn't check out branches or add worktrees.
5. Prove a wcgw breakage before raising it. Where it turns on how often something happens, check prod data first: if prod shows it doesn't happen, don't raise it, and list it as not raised with the count. Otherwise write a unit test that fails on the PR head, and share the test and its failure output in the comment. If the bug is obvious on reading the code, skip the test, except in a background run (step 10), where every breakage raised gets its test however slow. On my own PR, fix it; on someone else's, the comment names it, following step 7.
   - Run the test in a scratch worktree at the PR head named `review-<pr>-<sha7>-<slug>`, never in a worktree another session may be using. One Gradle run at a time: before starting, check `pgrep -fl 'worktrees/review-'` shows no other run. Read the result from `build/test-results`, not a shared log. Then remove the worktree, which ditches the test.
6. Run the naming, types, dry, safety, logging and readability skills, and the refine skill's checklist, in a subagent per stack, or per PR for one that isn't stacked. Doing it per stack catches a name that differs between PRs. Refine runs as a report: no edits, no checkout, no lint. Each subagent returns only its findings.
   - On my own branch, once its findings are fixed, also run refine's Verify step (lint, typecheck and prose lint), so the review covers everything `/refine` does.
   - Tests: prefer in-memory tests (`simulateAccount`) over repo tests. A repo test earns its place only for a flow that needs jobs, workflow actions or persistence. When the code under test reads the repo directly instead of taking an `AccountWrapper`, flag it: moving it onto `AccountWrapper` is what lets it be tested in memory. Don't flag a repo test that drives a workflow action, or code with no single account to wrap.
7. Draft the comments in my voice, following the PR comment rules in CLAUDE.md. Each comment ends with a line naming the skill or agent its finding came from (`--wcgw`, `--naming`, `--types`, `--DRY`, `--safety`, `--logging`, `--readability`, `--refine`), all of them when more than one raised it (`--DRY --naming`). A finding from my own reading alone gets no sign-off. List what was looked at but not raised.
   - Name the problem and stop. Offer a fix only where a clear principle or rule settles it (naming, duplication, dead code, line length, a CLAUDE.md or coding-standard rule); the author can work out the rest. Don't say a problem "isn't costing anything yet": nothing in an open PR is deployed.
   - The feedback is principled, never a feeling. Every comment states what it rests on: a CLAUDE.md, coding- or writing-standard rule (permalinked), a codebase idiom (with an example), a general principle said in words (one concept, one name; a type states what it holds), or the evidence of a defect (what breaks, counted in prod). No "I'd prefer" or other phrasing that reads as personal taste. Where the industry has a name for the principle, cite it by that name, crediting its source when it's well known, since a named principle can be looked up and carries its own argument: "make illegal states unrepresentable" (Yaron Minsky), "a sentinel value", "single source of truth". State the principle positively, as what the code should do: "The principle is to make illegal states unrepresentable." Never phrase it as a negation, like "…, against making illegal states unrepresentable": that reads as arguing against the principle. Cite the most specific principle that fits, and only one: when a skill already names it ("keep a word's established meaning"), don't add a broader one that says the same ("the principle of least astonishment"). The `--<skill>` sign-off says where a finding came from, not what it rests on: the author can't read my skills.
   - Open on what makes the point land: the problem when it is concrete and speaks for itself, the principle when the problem is spread across several places or doesn't show on its own why it matters. Never open on a detail the reader needs the rest of the comment to make sense of. Before posting, and again after every edit, split or merge, re-read each comment's first sentence against this: comments change one addition at a time, and the opening is what goes stale.
   - Fewer words: the problem, the principle and the ask. Leave the mechanics (parameters to add, tests that move, how to wire it) to the author, whose Claude can work them out. A comment past a few sentences gets paragraph breaks: the point, then the code, then any question on its own.
   - No implementation hand-holding. The principle already points the way, so the comment doesn't sketch the fix: no "as master did it", no "so X can then be required", no "saved the way Y is", no tour of the lines that would change. Set the problem up in a sentence, show it once in the code, name the principle, and stop. A finding the principle settles needs no ask beyond naming it. Before posting, delete every clause that describes the change rather than the problem.
   - No knock-on sentences: after the problem, no "So …" about its effect elsewhere (e.g. "So the call at `:113` doesn't show it can end in ManualReview"). The principle carries it; cite only the code that shows the problem.
   - Each ask sits right after the principle that backs it. Two asks behind one principle ("One concept, one name: perhaps a new name, and 'waiting' in the comments") read as if one rule settles both. When a comment holds two points, give each its own paragraph ending in its own ask, or split it. Never ask to change text that the same comment proposes removing.
   - A suggestion that refactors code elsewhere (another function or file) gets its own comment, anchored there, so it isn't buried mid-comment. A self-contained suggestion block that covers a few things in one place stays one comment.
   - Show the code, not a paraphrase of it. When two pieces of code disagree, quote both side by side ("This uses `today().plusDays(31)`, but signup below uses `today().plusMonths(1)`"), never a domain retelling ("renewing families get 31 days, new families a calendar month") that the author has to translate back into their own code. Then one concrete case where the difference shows (a 15 Feb sign-up gets 18 Mar or 15 Mar), then the ask.
   - Every code reference is a GitHub permalink to the PR's head commit, `[`File.kt:12-14`](https://github.com/<owner>/<repo>/blob/<head-sha>/<path>#L12-L14)`: each comment's anchor, each citation inside it, and each item in the not-raised list. Cite code from another PR in the stack at that PR's head. The drafts and the posted comments carry the same links.
8. Once I approve, post one review per PR with inline comments. Right before posting, check the PR is still open and its head hasn't moved. If it merged, don't post on it; tell me, so anything still true on master can go elsewhere. If the head moved, recheck each comment against the new commits. A review still pending when its head moves goes stale: delete it and recreate it on the new head, with each anchor and permalink moved to match.
9. When the author replies, check each reply against the new commits, not its own claim. Report what's fixed, what they pushed back on and why, and anything new, with links to the PR and the commits to read. Approve only when I say I've reviewed them. Once my comments are fixed and someone else has already approved, leave it: I don't need to approve too, so don't report it as ready or suggest approving. The exception is when the author has asked me for review since my last review (a `review_requested` event for me in the PR's timeline, not one left over from before): then, if the review of their changes leaves nothing to raise, approve it myself, with no body, and tell me. Likewise when my approval was dismissed, by a push or by the author: review what changed since it, and if that leaves nothing to raise, approve again myself and tell me. If the PR conflicts with its base when I approve, then post a short heads-up tagging the author, without naming files or asking for anything: "@<author> heads up, this has a merge conflict."
10. In a background run (started from `/loop` or `/pr-loop`, nobody watching):
   - Each wake-up, list the open non-draft PRs requesting my review, and the PRs holding a pending review of mine whose head has moved. Nothing new: end the turn with no message.
   - Authors forget to re-request review, so also list the open PRs I've reviewed but not approved whose author has since pushed or replied in my threads. Act once every inline comment of mine is fixed or replied to, by step 9 and a review of the new commits; until then they're still working, so stay quiet. A comment proven fixed in the commits needs no reply: don't hold back for one or mention that it's missing.
   - Review each by steps 2-7 and deliver it as a pending review (created without an `event`), so only I can see it. Never submit a review, post a standalone comment, or edit a comment I've posted, except the approvals step 9 allows (the author asked me, or my approval was dismissed) when there's nothing to raise, and the comment tagging the author when an approved PR conflicts with its base.
   - A pending review whose head moved: rebuild it on the new head, as step 8 says.
   - When a review is ready, send me a push notification naming the PR, linking the pending review, and saying for each bug finding whether a test proved it.
